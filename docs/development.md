# 开发规范

## 1. 开发方式

- 编码前明确问题、预期行为和验收方法。
- 一次改动只解决一个目标，功能、重构和无关格式修改分开提交。
- 优先复用现有模块，按需抽象。公共接口、依赖方向或范围变更先讨论，再同步文档。

## 2. 代码风格

- 遵循 [PEP 8](https://peps.python.org/pep-0008/)，使用 UTF-8、4 空格缩进和清晰的英文命名。
- 模块、函数、变量用 `snake_case`，类用 `PascalCase`，常量用 `UPPER_SNAKE_CASE`，内部实现以 `_` 开头。
- 公开接口写类型注解，说明参数、返回值和异常；注释解释原因与数学条件。
- 函数职责单一，避免重复逻辑、隐式全局状态和循环导入。导入按标准库、第三方库、项目代码分组，worker 延迟导入按实现方案处理。
- 安装项目解决导入路径，不临时修改 `sys.path`。

## 3. 模块与错误处理

- CLI 调用应用层；计算不依赖界面或 OCR，展示不补算答案或步骤。公开结果及嵌套字段须可 JSON 序列化，不含第三方数学对象。
- 输入问题和不支持能力返回明确诊断；只捕获能处理的异常，兜底放在应用或 worker 边界。失败不能当成成功或无解。
- 保留原始输入、定义域和条件，区分精确值、近似值、未求出与不存在，不擅改公式含义。
- 计算须有时限，异常、取消和超时均回收资源；日志与 JSON 结果分开。

## 4. 环境与依赖

- 使用项目虚拟环境；Python 和直接依赖以 `pyproject.toml` 为准，开发依赖组合以 `requirements-dev.lock` 为准。
- 新增依赖说明用途；升级同步配置、锁文件和环境记录，并验证兼容性与回归用例。
- 不提交环境、缓存、构建产物或凭据，IDE 配置只保留团队共享项。

## 5. 测试与验证

- 测试放在 `test/test_*.py`。行为变更补测试，缺陷修复补回归，覆盖正常、边界和失败场景。
- 验证数学语义，快照检查展示，数值比较明确容差；依赖、随机因素和超时任务须可控。
- 提交前跑相关测试，公共模型、执行流程或依赖变更跑完整测试。快照更新须核对原因；空测试、未收集或跳过不算验证通过。
- 纯文档改动检查内容、链接与格式。

常用检查命令（Windows 开发环境）：

```powershell
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m pip check
git diff --check
```

## 6. Git 与代码审查

- 提交独立、清晰，消息用 `类型: 变更说明`；类型为 `feat / fix / docs / refactor / test / chore`。
- 代码改动经另一位成员审查后合并；纯文档或格式改动可简化审查。PR 说明变更、原因、验证结果和未完成项。
- 重点审查正确性、模块边界、失败处理和测试；不混入无关改动，不覆盖他人工作。

## 7. 完成标准

- 预期行为可运行，适用范围与失败行为明确，相关测试通过；未验证事项如实说明。
- 文档已同步，审查问题已处理，无失效说明、调试残留和无关文件。
