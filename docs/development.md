# 开发规范

## 1. 开发方式

- 编码前明确问题、预期行为和验收方法。
- 一次改动只解决一个目标，功能、重构和无关格式修改分开提交。
- 优先复用现有模块，按需抽象。公共接口、依赖方向或范围变更先讨论，再同步文档。

## 2. 代码风格

- 遵循 [PEP 8](https://peps.python.org/pep-0008/)，使用 UTF-8、4 空格缩进和清晰的英文命名。
- 模块、函数、变量用 `snake_case`，类用 `PascalCase`，常量用 `UPPER_SNAKE_CASE`，内部实现以 `_` 开头。
- 公开接口写类型注解，说明参数、返回值和异常；注释解释原因与数学条件。
- 函数职责单一，避免重复逻辑、隐式全局状态和循环导入。导入按标准库、第三方库、项目代码分组，worker 延迟导入按实现方案处理。
- 安装项目解决导入路径，不临时修改 `sys.path`。

### 共享模型组织

- 数据模型放在 `src/mathlens/schemas/`，按类型归入现有文件，分类见
  [模型组织说明](schemas.md)。不要每新增一个模型就创建一个文件。
- `enums.py` 存放公开枚举；schemas 子模块存放结构，不加入计算、I/O、进程
  调度或运行时控制回调。
- Spec 的纯参数规则集中在自身 validate() 方法，返回 ValidationIssue，不在
  构造时抛输入异常。prepare 统一转换为响应，不按运算类型重复实现参数规则。
- 输入、符号、偏好和执行选项按同样方式自校验，请求组合嵌套问题。共用结构
  检查复用 schemas/validation.py，容量策略与数学参数是否合法分别处理。
- 避免提前引入注册表、流程框架或额外服务层；只被一处使用的容量策略保持
  为内部函数。父进程和 worker 已实际共用的预检集中在 preflight.py，不复制
  规则或反向导入 application。运行时控制类型独立于具体进程执行后端。
- 字段类型注解是调用契约，运行时结构校验通过接收 object 的工具处理；不要
  在已声明具体类型的字段上散写被静态检查器判为不可达的反向类型判断，也不
  将字段改成 Any/object 或添加忽略注释来消除告警。协议只用于实际需要的结构
  抽象，不为具体类检查附加 runtime_checkable。
- 业务模块使用 `from mathlens.schemas import ...`（包内可用相对导入）；
  schemas 内部直接引用具体子模块，避免通过 `schemas.__init__` 形成循环。
- 新公开模型和类型别名在 `schemas/__init__.py` 显式重导出，并加入 `__all__`。
- 修改模型字段、默认值、标签或语义时同步接口文档与 JSON 示例。仅移动定义
  不修改 JSON 契约，不为文件拆分提升 schema_version。
- 类型注解与 frozen dataclass 不替代输入校验；不要把未实现的约束写成已经
  可用的运行时保障。公共模型变更跑完整契约测试。

## 3. 模块与错误处理

- CLI 调用应用层；计算不依赖界面或 OCR，展示不补算答案或步骤。公开结果及嵌套字段须可 JSON 序列化，不含第三方数学对象。
- 输入问题和不支持能力返回明确诊断；只捕获能处理的异常，兜底放在应用或 worker 边界。失败不能当成成功或无解。
- 保留原始输入、定义域和条件，区分精确值、近似值、未求出与不存在，不擅改公式含义。
- 计算须有时限，异常、取消和超时均回收资源；日志与 JSON 结果分开。

## 4. 环境与依赖

- 使用项目虚拟环境；Python 和直接依赖以 `pyproject.toml` 为准，开发依赖组合以 `requirements-dev.lock` 为准。
- 新增依赖说明用途；升级同步配置、锁文件和环境记录，并验证兼容性与回归用例。
- 不提交环境、缓存、构建产物或凭据，IDE 配置只保留团队共享项。

## 5. 测试与验证

- 测试放在 `test/test_*.py`。行为变更补测试，缺陷修复补回归，覆盖正常、边界和失败场景。
- 验证数学语义，快照检查展示，数值比较明确容差；依赖、随机因素和超时任务须可控。
- 提交前跑相关测试，公共模型、执行流程或依赖变更跑完整测试。快照更新须核对原因；空测试、未收集或跳过不算验证通过。
- 纯文档改动检查内容、链接与格式。

常用检查命令（Windows 开发环境）：

```powershell
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m pip check
git diff --check
```

## 6. Git 与代码审查

- 提交独立、清晰，消息用 `类型: 变更说明`；类型为 `feat / fix / docs / refactor / test / chore`。
- 代码改动经另一位成员审查后合并；纯文档或格式改动可简化审查。PR 说明变更、原因、验证结果和未完成项。
- 重点审查正确性、模块边界、失败处理和测试；不混入无关改动，不覆盖他人工作。

## 7. 完成标准

- 预期行为可运行，适用范围与失败行为明确，相关测试通过；未验证事项如实说明。
- 文档已同步，审查问题已处理，无失效说明、调试残留和无关文件。
