## 已验证问题

### F1 · P1：解析器丢失 I 的幂和下标，仍返回成功

位置：src/mathlens/parsing/latex.py:67、78；关联 test/test_parsing.py、test/test_slice.py。

通过真实 spawn worker 调用 run，实测：

| 输入 | status | value.expression.text |
|---|---|---|
| I^2 | success | I |
| I_1+I_2 | success | 2*I |
| I_1^2 | success | I |
| x_1+x_2（对照） | success | x_1 + x_2 |

latex2sympy2.convert_atom 遇到字母 I 就提前返回虚数单位，后续下标和上标处理
没有执行。适配层只检查转换后的表达式，并明确允许 I，因此无法发现信息丢失。
即使约定裸 I 表示虚数单位，I^2 也应为 -1；如果约定它是普通变量，也不能变成 I。

建议：先在转换前识别并拒绝会丢失含义的 I 写法，返回明确能力诊断；或者在当前
适配层正确处理其下标与整数幂。不要修改 site-packages，也不必自写整套解析器。
在保证语义前不能把这些输入标为 ready/success。补充上述公开 API 回归用例，
并明确保留常量名的约定。

### F2 · P2：codec 使用固定默认限制，执行配置不能控制 JSON 深度和容量

位置：src/mathlens/codec.py:134–148；关联 src/mathlens/execution.py:72、91、160、164。

_read 每次创建 ResourceLimits()，既不接收调用方限制，也不区分请求和响应。
_encode 又调用 _read，所以固定默认限制同时影响编码与解码。

已复现两种方向的偏差：

- run(x+x, limits=ResourceLimits(max_json_depth=1)) 返回 success；实际任务和响应
  明显超过一层，调用方收紧的深度限制未执行。
- 给 PrepareTask 的公式传入约 4.1 MB 文本，同时配置 max_input_bytes=5_000_000、
  max_output_bytes=6_000_000，任务在启动前仍报「JSON 超出默认容量」，且被
  execute 映射成 invalid_request。固定 4 MB 输出默认值限制了合法的输入配置。

建议：让边界编解码显式接收有效的字节与深度限制；独立公开 codec 入口可保留
默认值，执行路径必须传入本次任务配置。请求按输入容量检查，响应按输出容量
检查。补低于默认值和高于默认值两组测试，不只测 recv_bytes 的长度上限。

### F3 · P2：非法成功状态可以穿过 JSON 和 worker 接收边界

位置：src/mathlens/execution.py:91–98；关联 src/mathlens/codec.py:105–114、
schemas/preparation.py、schemas/results.py。

以下对象能够编码并解码成功：

```python
decode_response(encode_public(ComputeResponse(status=Status.SUCCESS)))
```

恢复结果为 success，但 problem=None、value=None、result_kind=none。
PreparationResponse(status=READY) 同样可缺少 problem。
进一步用测试 worker 发送前一种响应，run 原样返回了 success。

这违反 interfaces.md 中成功计算必须带实际问题快照、ready 必须带问题快照等
跨字段约束。现有 codec 检查字段类型，执行器只检查响应类，没有人检查响应状态
是否与内容一致。调用方按 success/ready 使用结果时会读到不存在的内容。

建议：在统一输出边界增加少量显式响应约束检查，拒绝非法 worker 结果并转换为
结构化错误；编码公开响应时也使用同一规则。无需让 dataclass 构造函数抛输入
异常，更不必把数学请求的完整 validate 逻辑搬入 codec。至少覆盖 ready 无快照、
success 无快照、value 与 result_kind/latex 冲突、needs_input 无补充项。

### F4 · P2：通道和 Process 构造位于异常处理之外

位置：src/mathlens/execution.py:80–83，保护执行的 try 从 102 行才开始。

把执行上下文的 Pipe 替换为抛 OSError 的实现后，通过公开 prepare 调用，
OSError 直接逃出；没有得到 PreparationResponse。系统句柄不足等通道创建失败
属于可预期执行失败，应遵循已声明的结构化错误契约。
如果 Pipe 成功而 Process 构造失败，已分配通道也没有进入 finally 回收路径。

建议：把执行资源的创建包含在同一异常与清理边界内，以明确的未创建状态跟踪
通道和进程。只清理已成功创建的资源。补 Pipe 构造失败、Process 构造失败和
start 失败三种测试，验证错误响应以及已分配资源的关闭。

### F5 · P2：深层合法模型在 JSON 转换前抛出裸 RecursionError

位置：src/mathlens/codec.py:159–170。

构造 501 层 children 的 CalculationStep 链，放入公开 ComputeResponse，再调用
encode_public，实测直接抛 RecursionError，异常没有 code。该输入应该因超过
JSON 深度限制而被拒绝，但 _json_tree 在深度检查之前递归展开，且调用位于
_encode 的 try 外。

建议：在模型展开时检查深度，超过限制就返回带 code 的 ContractDecodeError；
同时将展开过程包含在编码异常边界内。不要等完整树和 JSON 都分配好再检查。
加一条深层模型编码测试，区分资源限制与普通序列化错误。步骤生成虽然尚未
启用，CalculationStep 和 encode_public 已经是现有公开契约，所以边界仍需正确拒绝。

### F6 · P2：监督端抹掉已识别的协议、版本和深度错误

位置：src/mathlens/execution.py:120–122。

测试 worker 发送合法 JSON、合法 PreparationResponse，但 envelope 的
protocol_version=2。decode_worker_result 能识别 protocol_version_mismatch，
监督端却把它统一转换为 worker_failed。响应版本不匹配以及 codec 检出的资源
限制也走同一分支。调用方因此无法按稳定原因码区分版本兼容、容量问题和进程崩溃。

建议：为 ContractDecodeError 保留已知 code 和 field_path；EOF、崩溃、普通通道
错误继续映射 worker_failed。仍生成与任务匹配的本地错误响应，不暴露 traceback。
补合法 JSON 下的协议版本、公开版本和深度错误测试。

### F7 · P3：已跟踪的 PyCharm 模块根目录指向 .idea

位置：.idea/mathlens.iml:4–11；关联 .idea/modules.xml:5。

模块文件位于 .idea/mathlens.iml，$MODULE_DIR$ 因而是项目的 .idea 目录。
当前 sourceFolder 指向 .idea/src，而源码实际位于项目根的 src；Python 目录和
虚拟环境排除路径也有同类问题。SDK 名称还绑定了本机绝对路径。

建议：若保留团队共享模块配置，将 content/source/exclude 指向正确项目根，
移除本机 Python 分发目录和绝对 SDK 绑定；或者停止跟踪这类本机配置。
.gitignore 中已有 .idea/ 不会自动移除已跟踪文件。

### F8 · P3：实施文档仍把已经交付的能力写成后续任务

建议：标明哪些里程碑已完成，将末尾完成标准改为剩余运算的验收要求；准确
区分 test_contracts.py 的结构测试与全项目现有测试。不必扩充新文档体系。
